# 投递目标双形态：账本键新增 `target_kind` 并一次性迁移既有库

## 背景与动机

转发的接收方此前只有群一种形态，账本唯一身份固定为四字段：账号、源群、源消息
ID、目标群。本次变更把接收方扩为两种形态（目标群、私聊目标），同一个「目标」
字段从此要同时容纳群号与好友 QQ 号——而这两个数字空间是重叠的：源消息发往群
`12345` 与发往好友 `12345` 必须是两笔互不阻断的独立投递，否则防重会误判。

三种可选的键改法都有硬伤：

- **目标列写带前缀的标识**（群=裸群号，私聊=`private:<QQ>`）：零 schema 变更、
  零迁移，但两种命名空间挤进一个字段，读取方每次都要解析前缀，「目标标识」
  的语义随形态漂移，且格式约定散落在各处。
- **`target_kind` 作为非键列**：主键仍是四字段，群 `12345` 与好友 `12345`
  照样撞键，等于白加一列。
- **`target_kind` 进主键**：SQLite 不能 `ALTER` 改主键，必须整表重建既有库，
  与账本「完整原库保留、不自动回迁、验证不通过即关闭发送」的既有红线正面冲突。

操作者在阶段一明确选择第三种（接受整表迁移），因此本 ADR 记录该取舍与它的
代价，避免以后读者以为这是无成本的选择。

## 决策

1. `DeliveryKey` 新增 `target_kind`（取值 `group` / `private`）并进入主键，
   表结构随之改为五字段主键；`_validate_database` 同时接受新旧两种形状。
2. 既有四字段库在开库流程内完成**一次性迁移**：先取状态目录独占锁 → 只读
   验证原库完整性与既有记录 → 单事务内建新表、按既有行回填
   （`target_kind='group'`）→ 校验记录数与状态一致 → 替换原表 → 提交。迁移
   只在「确认新装才建库」之外的新装/升级路径上发生，不删除、不改写、不回迁
   任何既有状态类证据。
3. 迁移过程中任一步校验不通过、形状不可识别、独占失败或写入未确认：保留原
   文件并按账本不可用（`ledger_unavailable`）关闭发送，不降级为四字段继续
   运行，不新建空历史，不假称迁移成功。
4. 迁移前的备份是运维前置条件；回滚旧代码前必须恢复该备份，因为新库对旧代码
   的严格校验不可读。迁移后新增的私聊投递记录在回滚后不可见，须先导出或人工
   记录，不得悄悄丢弃。

## 后果

- 防重语义与目标形态解耦：同一源消息对群与对同号好友互不阻断，「同消息不同
  目标」的既有场景自然覆盖两种形态。
- 升级路径多一次不可逆的库结构变更，运维必须先备份；这是为「两种命名空间不
  混在一个字段」付的成本。
- `target_kind` 成为投递身份的一部分后，结果面与日志需按形态展示目标（群号或
  对端 QQ 号），否则同号群与好友在人工核对时无法区分。
- 若未来再出现第三种目标形态（如临时会话），只需扩展 `target_kind` 取值，
  不必再改主键结构。

## 备选方案（未采纳）

- 目标列前缀方案：实现最省，但把类型编码进数据、读取方到处解析，且与
  「账本只存必要投递事实」的口径不一致。
- 非键 `target_kind` 列：不解决撞键，且让唯一性依赖应用层检查，与主键保证
  重复发送阻断的既有机制脱节。
- 迁移失败回退四字段运行：会同时存在两种 schema 的账本真相，违背「唯一活跃
  账本、验证不通过即关闭发送」。
