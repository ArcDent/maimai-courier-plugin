# 嵌套卡片（卡片套卡片）由「原状提交」改为「发送前整条拒绝」

## 背景与动机

2026-10-05 的卡片路径整改（`get_forward_msg` 展开 + `send_group_forward_msg`
节点重组）对嵌套内层卡片采取「原状提交、不递归展开」，契约写明「其在目标群的
展示不作保证」。2026-10-06 对真实实例的对比实测（授权测试群；源卡片 15 节点、
5 个内层 [聊天记录]）证伪了该契约的可用性，三种投递形态都无法保留内层信息：

- 旧 res_id 原样提交（当时的现行契约）：目标群客户端内层显示为降级空壳
  （`#000000 / 34 / 聊天记录 / function(){[native code]}` / 查看转发消息）；
- `upload_forward_msg` 重传内层节点取得新 res_id 后由外层引用：**同样**是空壳，
  且内层 reply 段被静默丢弃（首个内层 3 条变 1 条）；
- 递归展开拍平成一层节点：文本与图片内容可保留，但嵌套结构丢失，内层 reply 段
  在目标群显示「[原消息已过期]」。

同一轮只读结构核验表明：新旧两种引用的内层资源都能被 `get_forward_msg` 正常
展开——降级发生在客户端渲染层，与资源新鲜度无关。也就是说「原状提交」从来
没有真正可用过；继续放行只会产出「信封成功、回执核验通过、群内内容不可用」
的投递，与 2026-10-05 已禁用的 `send_msg` 直引旧 res_id 属于同一类陷阱。

## 决策

1. 「卡片消息转发」契约增加类型检查：展开取得的节点内容含其它合并转发卡片
   （嵌套 forward 段）时，**发送前整条拒绝**，不提交任何消息。当前只收这一种
   类型——它是唯一在实际应用中出问题的一类；判定族收敛在独立的类型检查模块，
   日后按同一模式扩充其它端点不支持的类型（如实测回执序列为 0 的
   `xml`/`share`/`contact` 节点内容、端点明确拒收的 `poke`/`market_face`）。
2. 拒绝发生在客户端准备阶段（展开查询之后、节点构造之前）。本地预检与自动入口
   的分类不联网、不提前判定。固定对外措辞：**「源卡片包含嵌套聊天记录，无法
   完整转发，不建议继续尝试」**；日志与结果面记可定位 reason 码。
3. 自动入口增加**只读预搜索**：仅对合并转发候选，在可读性确认与配置初检之后、
   目标名称查询之前，用与工具路径相同的两步只读查询（`get_msg` 取平台卡片标识
   → `get_forward_msg` 展开判定）预识别嵌套卡片；命中则不提供判断机会并记录
   可定位原因。查询失败、取不到卡片标识或结果不可判定时**放行**
   （fail-open）：自动判断不因端点抖动而静默失效，最终仍由工具路径权威拒绝。
4. 显式工具调用路径不受自动入口改动影响；嵌套拒绝发生在发送前，不产生平台
   副作用，不建账本记录、不改四字段键、不影响既有防重。

## 代价与不变量

- 代价：含嵌套聊天记录的卡片不再被转发（此前是「能发但内层不可看」）；自动
  入口为每个卡片候选多两次只读查询；预搜索使自动入口首次读取直连端点（只读、
  失败放行，不新增发送面）。
- 不变量：固定七动作不变（预搜索只用既有只读动作）；一次投递仍最多一次源
  发送加一次评论；四字段账本键、防重与结果状态机不变；普通文字/图片路径
  不受影响；「插件不递归展开、不改写节点内容」的边界不变——现在连一层嵌套
  都不再提交，由拒绝替代放行。

## 未确认项

- 降级空壳证据来自单一实例（SnowLuma 1.14.17-node）、单账号、一个授权测试群
  与一次客户端观察；其它客户端或版本未测。结论同步写入联验清单 U6，未替代
  真机目视联验。
- 「递归展开拍平保内容」路线本次不采纳，保留为未来选项（若未来要启用，拍平
  后的 reply/媒体展示需重新联验）。
