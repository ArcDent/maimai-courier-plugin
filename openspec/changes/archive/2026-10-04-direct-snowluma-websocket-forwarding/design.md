## Context

动机与范围见 [proposal.md](proposal.md)，当前架构决定见 [ADR 0007](../../../../docs/adr/0007-direct-snowluma-websocket-client.md)。主规格和运行代码仍以独立服务为基线；旧变更已经归档，但其真实 QQ 联验未完成，不能把归档当作部署事实。

本轮已读取的本地实现提供以下复用基础，而非新协议已通过验证的结论：

- `service/onebot.py` 已有固定端点、环境变量认证、串行请求与 `echo` 匹配；它依赖服务配置，且在动作调用时才消费 WebSocket，不能原封不动满足插件长期连接的空闲事件处理和生命周期。
- `service/gateway.py` 已有账号查询、源归属、目标群列表和目标回执核实；当前传输可在不同动作间重建连接，新设计必须防止账号核验与实际写入跨连接使用。
- `service/materials.py` 已有 OneBot 原卡片资源引用、普通内容转换与媒体安全校验；`send_material.py` 已有宿主普通消息预检和唯一宿主卡片形状判据。两种输入格式需要映射，不应复制提及呈现规则。
- `delivery_ledger.py` 仍有本插件原 SQLite 结构、四字段防重键与短事务；新设计需补齐独占打开、历史切换识别和可靠评论占位，而非恢复客户端/服务端双账本。
- `shared/delivery.py`、`shared/result.py`、`shared/mentions.py` 等已有共用类型和规则。目录名称不是删除理由，不能为“收缩共享层”复制第二套类型或状态机。
- 2026-10-02 用户授权调整第 1 组只读来源：`arcwsl:~/github/REFERENCE/` 不可达，改以 `arclinux` 部署机上的 MaiBot 宿主源码与已部署适配器源码为准；适配器是客户端实现，不能替代服务端实现。SnowLuma 网关服务端源码不可得，凡只能由其确认的字段与语义按 D10 作为显式假设处理。

截图仅证明已有正向 WS 服务端和当时的多客户端连接。各端点的身份、完整动作权限、多客户端响应隔离及可达地址均未由截图证明。报告中的宿主与适配器源码结论在第 1 组按可用来源重新只读核对前只作为线索，网关服务端结论按 D10 作为假设冻结；不在本次规划中伪称已完成远端核验。

## Goals / Non-Goals

**设计目标：**

- 以插件内一个直连执行入口封装连接、账号核验、可信源查询和回执检查；调用者无需理解 OneBot 任意动作协议。
- 将权限与持久事实留在现有编排及账本中，把传输变化限制在少量模块；正常发送只有一条路径。
- 先复用后收敛，维持来源凭据、候选分类、提及、结果渲染与时钟的单点语义。
- 从公开工具到本地模拟 WebSocket 的完整测试覆盖副作用边界，不只测新的传输类。

**设计排除：**

- 不搬回远程会话、心跳授权、挑战、HTTP 控制协议、双端账本身份或通用动作代理。
- 不增加新监听端口、多账号池、后台补发队列、自动回迁工具或替代宿主入站处理链。
- 不以可用性为由弱化未知阻断、证书校验、凭证保护或材料完整性。

## Decisions

### D1：原生正向客户端，不借适配器 API

新增活跃模块暂定 `snowluma_client.py` 与 `snowluma_transport.py`：前者收敛现有网关行为，后者从现有 `OneBotTransport` 与 `AiohttpOneBotTransport` 演进。仅插件组合根创建和持有它们，不启动子进程，不注册宿主发送网关。

对编排暴露“可信源准备、源发送、评论发送、关闭”这一小接口，优先复用现有 `PreparedSource`、`SourceMaterial`、`SourceSendResult` 与发送接缝，移除仅服务协议需要的字段，不另包一层远程客户端。测试通过同一接口注入内存或真实本地 WebSocket 替身。

舍弃替代方案：适配器 API 违背用户本次选择；原独立服务增加运行件；直接让 `plugin.py` 发原始动作会把账号、回执和错误分类分散到多个调用点。

### D2：最小直连配置与明确身份

配置新增 `[snowluma]`，字段暂定 `websocket_url` 与 `token_env_var`，默认均为空；保留原业务开关、白名单、自动候选与标准及宿主要求的配置版本。账号预期来自可信宿主 `SourceSession.account_id`，不增加模型参数或自动探测账号列表。

- 凭证只在建连时按环境变量名读取，不读取适配器运行文件，不在 URL 中携带凭证。地址禁止用户信息、查询凭证、片段和非 WebSocket 协议；`0.0.0.0`/未指定地址不作为连接目标。
- 沿用安全默认：`ws` 只允许本机回环，其他地址要求 `wss` 和证书验证（地址口径见 D11 修订）；不能把 Docker 内的 `localhost` 当成宿主机，也不根据截图自动写入端点。跨主机实际可达且受保护的端点由部署者准备，不为本轮规划擅自配置服务器。
- 通过所选网络库实际接口保证握手重定向不被跟随；第 1 组核实是否可直接禁用。若库未提供所需能力，在传输内部用经核实的握手机制实现，不能编造 `ws_connect` 参数或先泄露凭证再拒绝。
- `_manifest.json` 继续作为插件依赖唯一声明入口；优先沿用当前 `aiohttp>=3.14.3`，规划阶段不安装。不得因为退役 HTTP 服务就误删 WebSocket 依赖，不新增 `api.call`、`send.*` 或 `chat.open_session` 能力。
- 老 `[service]` 配置不映射为新端点，存在时给出明确退役诊断；保留其状态线索供 D6 检查，不据此联网。

总开关关闭或配置不完整时可以加载工具，但不建立平台连接。连接按合法请求需要建立，不维持后台自动重连循环。

### D3：单连接、单接收任务、有限串行执行

每个插件实例只持有自己的一个活动连接及一个接收任务；接收任务登记在本插件任务表，空闲时也持续消费并丢弃无关平台事件，不保存聊天缓存。平台心跳与自发事件不会进入 `auto_entry`、宿主数据库或模型。

保留传输串行化，不引入多连接池或无界响应表；当前动作只保留一个待决响应槽。关联标识组合运行实例随机标识、连接代次和递增序号，只有本连接、本动作、合法响应结构匹配时才完成等待；含平台事件标记的载荷不能仅凭相同 `echo` 冒充响应。

工作容量初始沿用旧服务的量级：最多 8 个在途工具投递，一个平台动作在执行；不另建无界排队队列，超限在发送前返回繁忙。动作排队计入该动作期限。WebSocket 帧大小设固定上限，初始 4 MiB；超限关闭本连接并按是否已提交分类。临时源材料只存在于有限在途投递中，完成即释放。

时限复用既有代码常量并统一到注入时钟：单次排队/动作总期限 10 秒、回执核验总预算 3 秒/最多 8 次/间隔 0.5 秒、评论等待 0.5 秒、卸载总等待 5 秒。建连包含在动作期限内，不叠加原传输 30 秒造成突破；剩余预算耗尽立即停止，不用最小查询等待额外延长期限。自动入口的既有 10 秒可读等待与 10 分钟/4096 项去重保持不变。

断线会失效待决响应和账号核验，不重放动作。后续独立操作可以按同一受控配置重新建连；新连接代次不能接收旧响应。关闭、取消接收任务与异常清理均有界，不能在超时处理的 `finally` 中无界等待不合作协程。

### D4：可信准备与提交前最后复验

保留 `source_binding.py` 和本地 `forward_precheck.py` 的可信入口；本地预检不发送、不访问 SnowLuma。预检通过后把可信源会话、源消息与目标交给直连执行入口，按固定顺序做账号核对、目标可用性、源查询、归属及材料构建。

宿主消息 ID 与 OneBot 源消息 ID 的对应必须经第 1 组源码核实，不能只调用字符串转换就认为可靠。账本键继续使用兼容的可信源身份；需要平台标识映射时单独保存本次内存查询标识，不改变旧防重键。宿主取得可恢复图片只是预检证据，不能把任意宿主路径直接交给远端 SnowLuma。

在源/评论取得发送执行机会后，完成必要的只读账号核验并固定当前连接代次，最后调用同步的 `_send_allowed` 复验当前卸载状态、总开关与两级白名单，同时确认连接配置代次及预期账号仍匹配。此复验必须在所有可能长等的查询和排队之后、实际写入之前；复验与开始提交之间不再放入其他异步工作。

固定连接若在核验后断开，不在该发送阶段自动重连；返回明确未提交或未知，取决于是否已经进入写入。连接/凭证引用改变时推进本地配置代次，阻止旧投递的后续阶段，尤其不能在新账号上继续旧评论。这里只是本地失效标识，不恢复远程阶段授权协议。

### D5：一个材料规则来源，一个回执判据

`send_material.py` 继续持有宿主形状识别与普通消息预检；把 OneBot 输入的材料映射从旧 `service/materials.py` 收敛到同一材料责任范围，使用不同入口处理宿主段与 OneBot 段，复用同一提及文本规则和共享类型。原卡片只处理唯一顶层资源引用，不递归提取内部节点。

图片仍必须可完整、安全重放。旧实现的 https 媒体引用路径是复用候选，不凭报告认定网关拒绝所有 `file`/二进制字段；第 1 组冻结经核实的输入输出形态。对于本轮无法安全重放的具体材料整条拒绝，不能把全部图片支持悄悄删掉。若维持图片支持需要改变用户边界，暂停返回需求对齐。

源和评论均使用一个固定群发送动作，优先沿用现有 `send_msg` 群分支；不在错误后换为 `send_group_msg` 或 `forward_group_single_msg` 探测重发。动作名与字段以核实记录为准，不直接采用报告示例。

回执复用既有有限 `get_msg` 核实：除目标群、绑定账号、正整数平台群序列外，还核对返回的 `message_id` 确实等于本次被查询 ID。当前报告所谓“三重核对”不能漏掉第四项记录身份。签名、响应结构与平台序列含义先核实；查询只针对本次回执，不通过模糊搜索或其他客户端事件拼凑成功。

### D6：恢复本插件原账本，先判历史再允许创建

`delivery_ledger.py` 重新成为唯一活跃账本；保留固定文件名 `delivery_ledger.sqlite3`、四字段键和原行的兼容读取。数据库短事务内原子占位，绝不持有事务等待网络。

打开顺序固定为：本插件数据目录独占使用权 → 检查本插件历史切换证据 → 验证现有数据库结构与记录 → 必要的兼容扩展和恢复 → 允许发送。独占锁实现优先从既有服务状态锁提取，而非仅靠“约定单实例”；无法取得锁时不运行恢复。

- 完整原账本：保留成功/未知及评论结果，`sending` 恢复为 `unknown`；兼容补充评论发送前占位及启动恢复，不复制服务端尝试/会话表。
- 新装：只有能够按宿主授予的本插件目录状态确认为新装时才初始化，不把数据库“缺表”或有历史痕迹的“缺文件”当成空历史。具体本插件历史文件名从现有代码核实，不扫描其他插件目录。
- 已有 `service_binding.json`、原账本归档、损坏/不匹配库或其他无法确认历史：保持 `ledger_unavailable`，记录非敏感原因，不联网读服务数据库、不自动回迁、不删除收据。后续人工处置另行规划，不以一个“忽略迁移”开关绕过。

评论状态附属源行；发送前需以短事务从允许状态转入评论 `sending`，恢复时仅把未完成评论归 `unknown`，不能改掉源 `sent`。完整落账后才能在结果里说评论状态可靠。成功/未知记录无 TTL 清理，临时材料不进账本。

### D7：编排与八态结果保持单一来源

`forward_delivery.py` 保留流程职责，但依赖从远程服务改为本地账本和直连执行入口：

1. 本地预检后复查卸载标记，先查已有投递事实，重复调用直接返回，不查询后补发。
2. 直连只读准备；失败明确未发送。通过后重新检查权限和连接配置代次，原子登记源 `sending`，并发未获资格者返回现有结果。
3. 进入源执行，在真正写入前执行 D4 最后复验；明确未提交则登记可重试失败并按权限拒绝等具体结果返回，可能提交则未知，可靠成功立即登记 `sent`。
4. 源已可靠落账且本次评论非空，等待固定 0.5 秒；再次复验、评论持久占位、提交前最后复验，最多提交一次评论动作，立即登记其结果。
5. 任一阶段已知成功但终态写入失败，保留占位阻断重发、停止后续工作，使用 `render_forward_result` 报告真实目标 ID 及持久性限制；不把落账失败渲染成完整成功。

继续使用既有 `DeliveryResult`、`SourceSendResult`、状态字面量与 `render_forward_result`，错误分类只集中在一个位置。新增的传输“未进入写入/可能已进入写入”证据是内部状态，不扩展模型可见的通用动作能力。未经核实的网络异常或平台错误默认未知，绝不通过异常文本猜测明确未发。

### D8：卸载与热更新只管理自己的工作

组合根持有时钟、账本、直连客户端及带定位描述的任务表。卸载先置停止标记使 D4 立即拒绝新提交，再有界结束本插件任务、停止接收、关闭本连接与账本；所有步骤共享 5 秒预算，超时逐条告警，不能误释放仍会被残留写入任务使用的账本后让新实例接管。

如果残留任务无法安全结束，保持发送关闭，并由退出清理确保其无法新提交；记录无法完成资源释放的事实，不能称“全部退出”。已提交操作保留真实回执或未知，不发送撤回消息、不注销 QQ 账号。

热更新候选类型与标准延续原语义：仅取消失效自动任务；只改标准不取消仍合法等待。权限变化使未提交源/评论被最后复验拦截；不整体取消所有投递掩盖实际副作用。连接配置变化使旧配置代次的未提交阶段失效，不迁移旧评论。

### D9：历史非删除式隔离，活跃共享逻辑不复制

历史材料归入 `history/snowluma-forward-service/`，形成明确的非运行区域；第 1 组先产出逐项保留/复用/隔离清单及内容核对记录。保留旧服务、客户端、专属测试及其依赖源文件快照，尤其保留未跟踪文件，不能假定 Git 已保存它们。采用可逆搬移或保存完整快照后退役原入口，不做不可逆删除，不使用 Git 写操作。

- 活跃代码不从历史目录导入；保留原路径兼容入口时只能明确退役，不能调用旧发送。
- `tests/` 只保留活跃测试；历史专属测试移到历史区，默认收集与 `pyrightconfig.json` 明确排除该区。保留旧测试不等于要求它们继续随新插件运行。
- `conftest.py` 清理远程客户端、服务协议及不再需要的顶层别名；必要共享类型继续解析到唯一对象。历史区不通过 `sys.path` 或别名补回活跃导入。
- 服务项目的 `pyproject.toml` 随历史隔离，不作为插件依赖入口；当前服务操作手册标为历史资料，新运行文档只描述插件直连。
- `shared/` 中仍被多个活跃模块使用的纯类型和规则保留；仅服务控制协议归历史。不为目录美观另造整套 root 类型，也不让历史版本与活跃状态机互相导入。
- `host_send.py` 继续作为退役墓碑；规则说明同步为新架构，保留 `CLAUDE.md → AGENTS.md` 软链接。

### D10：未复核的服务端契约按假设冻结，并以放行门槛兜底

SnowLuma 网关服务端源码在本轮不可获得，因此凡只能由服务端源码确认的事实（固定发送动作的参数形态、卡片资源字段、图片可重放字段、回执证据字段与含义）一律按既有研究报告作为**显式假设**冻结：在核实记录中逐项登记证据强度、替代来源与待确认清单，不写成已核实结论，也不用报告转述冒充复核。

对策不是放宽安全口径，而是让假设错误只能表现为「不确定」，不能表现为「错误地确定」：

- 一切未取得可确认证据的发送结果、异常与契约外取值按 `unknown` 处理，绝不因假设字段缺失而判为明确未发送或成功；
- 不因假设不成立而更换动作、通道或重发；
- 联验前不宣称已支持该事实；真实 QQ 联验（另行授权）必须逐项确认待确认清单，确认失败即回到规划，不得由实现者就地改口径。

### D11：实机部署暴露的两处口径修订

2026-10-04 在真实 MaiBot 部署（`arclinux`）上安装直连版后，两项设计假设与现场布局冲突；用户确认按以下口径修订，其余安全约束不变。

1. **状态目录等于插件目录**：宿主授予的 `ctx.paths.data_dir` 就是插件目录（旧账本即写在插件目录内），因此目录里必然同时存在源码、文档与配置备份。原 D6 的“目录只允许固定状态文件”会把正常部署判成“未核对的历史条目”，使发送永久关闭。修订为**只阻断状态类证据**：服务收据（含临时文件）、主库以外的数据库文件与归档副本、缺主库的孤立伴随文件、链接文件，以及子目录内一层名字命中的同类证据；插件自身的源码、文档、配置与缓存不再阻断。需要人工核对的证据一个不放行，只是不再把部署文件当证据。
2. **同主机网络内的明文端点**：SnowLuma 与插件在同一 Docker 网络，唯一直接可达地址是容器名的明文 `ws`，而 D2 要求非回环必须 `wss`，导致端点无法配置。修订为：`ws` 允许回环，**并在建立连接前确认目标解析为回环、私有或链路本地地址**，否则拒绝连接且不发送；公网目标仍必须 `wss`。地址校验保持离线字面量判断，地址族判定放在建连前的解析步骤，因此不依赖配置期 DNS，也不因主机名形态放行公网目标。

两处修订只放宽“可用性”，不放宽“发送正确性”：证据不明仍然关闭发送，明文目标不满足私有条件仍然拒绝。

## Risks / Trade-offs

- 截图不证明协议隔离或任意客户端可执行动作 → 首组核实实际版本的 WebSocket 分发、认证和响应路径，模拟多客户端干扰；真实端点接入留给获准联验。
- 报告与真实源码可能不一致，且服务端源码本轮不可得 → 首组只用可用来源记录基线与反例，服务端字段按 D10 假设冻结并登记待确认；实现侧未知优先，保证假设错误不产生错误确定。矛盾或假设不成立时暂停后续组、回到规划，不由实现者暗改规格。
- 非本机明文端点不能直接使用 → 保留传输保护，部署时提供可达的受保护端点；不擅自改 SnowLuma、反向代理或容器配置。
- 账号查询与发送之间无法获得 QQ 事务锁 → 固定已核验连接代次、每阶段复验、对真实回执再核对账号；不宣称能阻止服务端在一次写入内部自行切换账号。
- 长连接推送可能洪泛 → 单接收任务、不缓存事件、有帧上限、动作绝对期限和公平让出执行，验证空闲及洪泛下内存与卸载上界。
- 原账本缺失无法证明没有历史 → 先查本插件切换证据和目录状态，不能确认则关闭；本轮接受人工核对成本，不牺牲防重。
- 原资源失效、媒体不可重放及回执查询不可用 → 整条拒绝或未知，绝不降级内容或换通路重发；跨群展开及提醒行为不作离线保证。
- 历史区体积仍存在 → 换取未提交实现的可追溯保留，但禁止把它纳入运行和默认验证；后续清理必须用户另行决定。

## Migration Plan

1. **实现前核实**：在授权的只读范围内核对 MaiBot 宿主源码（`arclinux` 上的 `src/plugin_runtime/`）与已部署适配器源码，不读取运行配置、凭证、`data/snowluma` 运行目录或真实消息。固定客户端可证的认证/响应归属、ID 对应与历史清单，生成合成样本；网关服务端侧字段按 D10 作为假设冻结并登记待确认清单。无法从可用来源确认的项不写成已核实。
2. **离线返工**：先建立不联网默认及直连测试接缝，再复用传输/材料/账本，最后接入编排和生命周期；历史隔离按清单保留全量内容。各组完成后验收并修复，不抢先恢复发送。
3. **活跃验证**：保留无网络依赖的单元命令和带 `aiohttp` 的本地传输完整命令，分别统计结果；类型检查仅涵盖活跃生产代码。新增证明没有旧 HTTP、适配器 API 或宿主 fallback 的导入/调用检查。
4. **文档与规格交付**：更新 README、操作与联验清单、规则和术语中的过时实施归属；主规格同步及归档由用户另行授权。`cross-group-forward` 的 Purpose 不受增量正文自动替换，获准同步时需单独改为插件直连；旧服务需求全部移除后仅剩 Purpose 的能力文件按同步规则处理，不在本阶段直接删主规格。
5. **部署前人工门槛**：操作者保持总开关关闭，核对自己原账本完整性、连接地址及环境变量注入；存在服务权威切换证据则停止，不自动回迁。所有新配置缺省均不能发送。
6. **真实 QQ 联验**：另行授权后验证多客户端并存、账号一致、原卡片可展开、普通提及不提醒、评论顺序、断线未知及重启防重。未授权时明确标为未执行，不虚勾验收。
7. **回滚**：先关闭新路径并保留最新本地账本；不得直接启动旧独立服务或用陈旧快照重新发送。只有核实目标版本能完整保留新投递事实后才人工切换，否则继续保持关闭。

本设计没有留给实现者自行决定的产品分歧。第 1 组是协议事实验证关口而不是另选架构的授权；字段、版本或库能力与假设不符时必须提交证据并按影响回到规划，不绕过关口执行后续发送实现。
