## Context

现状约束（详见 proposal.md - Why 与 specs/ 两份 delta）：

- 目标只有群一种形态，工具公开参数固定为 `message_id` / `target_group_id` /
  `comment`；私聊目标、群号空间与好友身份在账本、预检与直连链路上都不存在。
- 分组判定族（`forward_group_entries` / `forward_group_of` /
  `shared_forward_group` / `source_group_is_allowed`）只在 `forward_precheck.py`
  单点定义，预检、源与评论提交前复验、自动入口共用。
- 账本表主键为四字段（账号/源群/源消息 ID/目标群），`_validate_database` 用
  `PRAGMA table_xinfo` 逐列严格校验，未知结构即拒绝打开。
- 固定动作集为七个；`snowluma_transport` 没有任意动作代理。
- 2026-10-08 实测结论（`docs/snowluma-http-api-catalog.md` 6.10）：私聊文字、
  单/多节点卡片、https 图片段均可用 `send_msg` / `send_forward_msg` 的
  `message_type:"private"` + `user_id` 路由投递；私聊回执带正整数
  `message_seq`、`target_id` 为对端、`user_id` 为机器人自身；负值目标消息 ID
  照常可按原值回查；名册外目标被平台以 `retcode=100` 拒绝。

## Goals / Non-Goals

**Goals:**

- 在不新增发送动作、不放宽可靠成功判据、不削弱既有防重的前提下，把投递目标从
  单形态（群）扩为双形态（群/私聊），并用分组开关把私聊面收口到显式开启的分组。
- 私聊目标的「选谁」由模型依据只读名册自行决定，插件只做可判定的核验，不做
  不可判定的匹配。
- 账本、预检、阶段复验、自动入口、结果面对双形态共用同一套口径，不出现第二份
  目标判定。

**Non-Goals:**

- 不做好友备注/昵称匹配、拼音匹配、候选收敛或「插件猜目标」。
- 不把私聊目标纳入自动入口的举荐范围（仅由显式工具调用发起）。
- 不为私聊放宽任何回执、成功判据或防重约束；不引入具名私聊发送动作。
- 不做多账号、临时会话（private/group）、对端客户端展示（头像/卡片渲染）的
  联验承诺。

## Decisions

### D1 私聊目标由模型从名册自选，插件只核验好友关系

模型先用只读工具 `list_forward_friends` 取得名册，自行选择 QQ 号，再以
`target_user_id` 调用转发工具；插件只判定「该 QQ 号是否为当前账号好友」。

- 备选：插件按备注/昵称做包含匹配。否定的原因：匹配是语义活，模糊、多命中、
  空命中都要定义行为，且把「谁可以收到源群内容」的判定从模型移到不可解释的
  字符串规则上；实测已确认平台对非好友本身就会拒绝，插件侧核验只需做好友
  关系这一件可判定的事。
- 备选：在转发工具拒绝时附带名册。否定的原因：会把名册塞进拒绝面，任何失败
  调用都回传一份好友数据；独立只读工具让「取名册」成为一次显式、可审计的
  只读动作。

### D2 名册工具与转发工具共用同一条一次性来源凭据链

`list_forward_friends` 无公开参数，凭据只由宿主 Planner 输出载荷签发、首次
消费作废。没有可信会话就无法定位「是哪个群在问」，也就不可能判定该群所在
分组是否开启私聊；复用同一条链还顺带守住「模型伪造会话/平台/账号字段一律
不读」的既有红线。名册条目上限取代码常量（500 条），超出即说明已截断。

### D3 固定动作集只增一个只读动作，私聊发送复用既有动作

动作集扩为：`get_login_info` / `get_group_list` / `get_msg` /
`get_forward_msg` / `get_friend_list` / `send_msg` / `send_forward_msg` /
`send_group_forward_msg` 与 `close`。私聊卡片与文字走 `send_forward_msg`
（`message_type:"private"` + `user_id`），私聊图片与评论走 `send_msg` 同参数。

- 备选：改用实测同样可用的 `send_private_msg` / `send_private_forward_msg`。
  否定的原因：新增两个发送动作会扩大「可提交的写入面」，且让「按源类型分派」
  之外再多一层「按目标形态选动作」的分叉；复用既有动作使目标形态只影响路由
  参数，不影响动作集合与分派结构。
- 备选：为私聊单独建一条客户端接口。否定的原因：直连链路只有一套有界预算、
  错误分类与回执核验，拆两份只会复制状态机。

### D4 回执核验按目标形态分治，一处定义

四项核验保留「ID 逐字 / 目标 / 账号 / 正整数 `message_seq`」，其中「目标」一项
按形态取值：群目标核验 `message_type` 为群且群号一致；私聊目标核验
`message_type` 为私聊、`target_id` 等于请求的私聊目标且 `user_id` 为机器人
自身。实测已确认私聊回执带正整数 `message_seq`，因此**不引入私聊特例的成功
判据**。负数目标消息 ID 的既有规则（按原值逐字比对）直接覆盖私聊。

### D5 账本键新增 `target_kind` 并一次性迁移既有库（ADR 0012）

`DeliveryKey` 增加 `target_kind`（`group` / `private`）并进入主键；既有四字段
库在开库流程内一次性迁移，既有行全部记为 `group`。

- 备选：目标列写带前缀的标识（群=裸群号，私聊=`private:<QQ>`），零 schema
  变更。否定的原因：用户明确要求独立列；前缀方案把两种命名空间挤进一个字段，
  读取方每次都要解析前缀，且「目标标识」的语义随形态漂移。
- 备选：`target_kind` 作为非键列。否定的原因：群 12345 与好友 12345 仍会撞同
  一把键，等于白加一列。
- 备选：迁移失败时按四字段继续运行。否定的原因：会出现「两种 schema 并存」
  的第二套账本真相，与既有「验证不通过即关闭发送」的红线冲突。

### D6 好友核验放在直连准备阶段，阶段复验只查配置层

`prepare_source` 在账号核对之后、源查询之前查一次名册并确认目标在名册内；
源与评论提交前的 `_send_allowed` 复验只查最新配置（卸载/总开关/同组判定或
分组 `private` 开关），不重复查名册。理由：好友关系是只读事实，配置才是会
热变化的许可；重复查询只会拉长在途时间。

### D7 分组判定族新增「私聊许可」单点判定

`forward_precheck` 在既有族内新增仅接收来源群的判定（来源群所属分组是否开启
`private`），预检、名册工具、源与评论提交前复验共用；成对判定
`shared_forward_group` 保持「来源 + 群目标」签名不变，从形式上继续杜绝「只判
目标」的越权用法。

### D8 名册数据的最小暴露面

名册只进一次工具结果（给模型选目标），不进日志、账本、投递结果与任务表描述；
日志只记「查询类别 + 条目数 + 是否命中」。工具结果与日志中的私聊目标只出现
QQ 号本身（它同时是账本键的一部分）。

### D9 自动入口零改动

自动入口的目标列举仍只列同组目标群；「私聊不进自动范围」由不举荐 + 不提供名册
满足。宿主 Planner 载荷不含「本次响应由主动唤起触发」的标记，因此不做、
也不能做「本次调用是否源自自动唤起」的硬判定；模型自行提交私聊目标时按显式
口径处理（见 specs 相应场景）。

### D10 凭据表支持两个本插件工具

`source_binding` 的清洗与签发从「只认 `forward_message`」扩为「认本插件的转
发工具与名册工具」两类；同批其他工具的调用仍原样保留且不获凭据。公开参数
声明按工具拆分，互不复用字段集。

### D11 传输层边界不变

2MiB 请求体上限、禁跟随重定向、禁代理、单实例锁串行、超时/断连/401 分类、
`close()` 幂等等既有约束全部沿用到 `get_friend_list` 与私聊路由参数上，不为
私聊新开任何例外。

### D12 图片路径到私聊与群路径同一材料形态

图片段沿用 `send_material` 的 `{"type":"image","data":{"url": https…}}` 形态；
实测该形态私聊可用，而本地 `file` 引用与群路径一样被平台以 `retcode=100`
拒绝，因此不新增图片处理规则，只补用例固化。

## Risks / Trade-offs

- [既有库迁移出问题] 迁移在单事务内完成并先做完整性校验；任何失败都保留原
  文件并按 `ledger_unavailable` 关闭发送，不新建空历史、不自动回迁。
- [迁移后回滚旧代码] 新库含 `target_kind`，旧代码的严格校验会拒绝打开。迁移
  前必须先有备份；回滚策略见 Migration Plan，不宣称无损回滚。
- [名册进入模型上下文] 仅 `private` 开启的群可见，条数有上限，不进日志与账本；
  仍然是「把好友身份交给模型」的固有暴露，由开关显式授权。
- [模型选错对端] 好友核验只保证「是好友」，不保证「是想要的人」；结果面明示
  对端 QQ 号，账本按五字段键防重，误投后同一投递被阻断、需人工核对。
- [目标形态分治漏判] 私有判定与成对判定都单点定义，预检/复验/名册工具三处
  共用，测试对每种形态各覆盖拒绝与放行。
- [实测快照边界] 结论来自单实例（1.14.17-node）、单账号、一个授权测试群的
  一次授权时段；多账号、其他版本、对端客户端展示未验证，不写进保证。

## Migration Plan

1. 部署前备份账本文件（含 `-wal`/`-shm` 若有）与配置；记录部署前哈希。
2. 代码与配置一起部署：`plugin.config_version` 提升（宿主先注入配置再回调），
   `private` 默认 `false`，因此升级后既有行为零变化、无自动发送。
3. 首次打开发送路径时完成账本迁移：独占 → 只读验证 → 事务内建新表并回填
   （既有行 `target_kind='group'`）→ 校验记录数与状态 → 替换 → 提交。失败即
   保留原文件并关闭发送。
4. 灰度：先在测试群所在分组打开 `private`，用名册工具与一次私聊显式调用验证
   端到端，再推广到其它分组。
5. 回滚：停用插件 → 恢复迁移前的账本备份 → 回退代码与配置。若已产生私聊投递
   记录，回滚后这些记录对新代码不可见，须先导出或人工记录，不得悄悄丢弃。

## Open Questions

- 私聊对端的客户端侧展示（头像、卡片内媒体渲染效果）未做目视联验，留待
  `docs/real-qq-validation.md` 逐项确认。
- 多账号、临时会话（private/group）与其他 SnowLuma 版本行为未测；若将来支持
  多账号，需重新评估名册与回执按账号分判的措辞。
